# 03 · 渲染图框架详解(myvk_rg)

## 1. 概述

`myvk_rg` 是一套**声明式渲染图(Render Graph)框架**,位于 `dep/MyVK/include/myvk_rg/`(接口)与 `dep/MyVK/src/rg/`(执行器)。它解决实时渲染器中最繁琐的三类问题:

1. **资源生命周期与复用**(内存分配、别名);
2. **同步**(barrier 插入、RenderPass 子通道合并);
3. **描述符管理**(按 Pass 自动生成 layout/set)。

使用方式(见 `rg/NRCRenderGraph`):

```cpp
// 1. 创建资源
auto v_buffer = CreateResource<ManagedImage>({"v_buffer"}, VK_FORMAT_R32G32_UINT);
// 2. 创建 Pass 并声明输入/输出(通过 AddInput / AddDescriptorInput / AddColorAttachmentInput)
auto vbuffer_pass = CreatePass<VBufferPass>({"vbuffer_pass"}, args);
// 3. 把某 Pass 的输出接给另一个 Pass 的输入(Input 构造时引用前者的 output alias)
```

## 2. 接口层(interface/)

### 2.1 对象模型:ObjectBase 与事件

所有实体(渲染图、Pass、资源、输入)都继承 `ObjectBase`,它维护:

```cpp
RenderGraphBase *m_p_render_graph;   // 所属渲染图
const ObjectBase *m_p_parent_object; // 父对象(PassGroup 等)
const PoolKey *m_p_key;              // 在当前池中的键
mutable void *m_p_executor_info;     // 执行器缓存(编译信息),const 对象也可写
GlobalKey GetGlobalKey() const;      // 父键 + 自身键,唯一标识
void EmitEvent(Event event);         // 通知执行器"某类数据变了"
```

**事件系统是增量编译的基石**。执行器监听 `Event`(见下),把"改动"映射为"需要重编译的阶段",避免整图重编译:

| 事件 | 触发场景 | 重编译阶段 |
| --- | --- | --- |
| `kPassChanged` / `kResourceChanged` / `kInputChanged` | 增删 Pass/资源/输入 | 全部(Collection 起) |
| `kResultChanged` | 改 result(输出别名) | Dependency 起 |
| `kCanvasResized` / `kImageResized` 等 | 尺寸/映射变化 | Metadata 起 |
| `kAttachmentChanged` | 改附件/子通道 | Schedule 起 |
| `kDescriptorChanged` | 改描述符输入 | VkDescriptor |
| `kExternalImageLayoutChanged` 等 | 外部资源同步 | VkCommand |
| `kUpdatePipeline` | 要求重建管线 | 立即重建 |

### 2.2 Pass 体系

```
PassBase (抽象:类型 + CmdExecute)
├─ GraphicsPassBase  — 光栅化:附件 + 描述符 + RenderPass/子通道
├─ ComputePassBase   — 计算:描述符 + compute pipeline
├─ TransferPassBase  — 传输(预留)
└─ PassGroupBase     — 组合 Pass:内含一组子 Pass(如 NNTrain 的 4 个子 Pass)
```

- **GraphicsPassBase**:额外管理 RenderArea(可固定、可用函数按 canvas 推导、可清空),`AddColorAttachmentInput` / `AddDepthAttachmentInput` 声明附件,框架据此建 RenderPass 并决定子通道合并;
- **ComputePassBase**:只声明描述符输入;
- **PassGroupBase**:`CreatePass` 创建子 Pass,`GetPass` 按 key 取回,`CmdExecute` 为空(由执行器遍历子 Pass)。

每个 Pass 的**管线创建**是延迟的:派生类实现 `CreatePipeline()`,框架在需要时调用并缓存(`VkCommand::CreatePipeline`)。

### 2.3 Resource 体系

```
ResourceBase
├─ BufferBase
│   ├─ ManagedBuffer    — 框架分配内存,可映射、可设 size/sizeFunc
│   ├─ ExternalBufferBase — 引用外部 myvk::Buffer(InputBuffer / AccelerationStructure)
│   └─ CombinedBuffer   — 由多个子缓冲"拼接"成一个大缓冲(内存别名)
└─ ImageBase
    ├─ ManagedImage     — 框架分配,可设 format/size/loadOp/clearValue
    ├─ ExternalImageBase — 引用外部 ImageView(InputImage / SwapchainImage)
    └─ CombinedImage    — 多个子图像按层拼成一张大图(array layers 别名)
```

**别名机制(Alias)**:`CombinedImage/CombinedBuffer` 允许把多个逻辑资源**并排放进同一块显存**(如多个互不冲突的临时图像共享一个大图像),`Metadata` 阶段计算每个子资源的 offset/layer,`VkAllocation` 阶段一次性分配。

### 2.4 Input 体系与 Usage

`InputBase` 描述一次"资源访问":绑定哪个资源(通过 Alias)、怎么用(`Usage`)、在哪个管线阶段、绑定到哪个描述符位点。

`Usage` 枚举(interface/Usage.hpp)是**框架的语义字典**,每个值编码了:

```cpp
struct UsageInfo {
    bool is_descriptor;
    VkDescriptorType descriptor_type;
    VkAccessFlags2 read_access, write_access;
    VkPipelineStageFlags2 stage;             // 指定管线阶段
    VkImageLayout image_layout;              // 该用法下的期望布局
    VkFlags resource_creation_usages;        // 创建资源时需带上的 usage 位
};
```

例如 `kStorageBufferRW` → 描述符 `STORAGE_BUFFER`、access 读写、stage COMPUTE、layout 由 shader 决定、创建时加 `STORAGE_BUFFER`。**所有下游决策(屏障 access、布局转换、描述符类型、资源创建 usage)都从这一个枚举派生**,是框架的核心抽象。

### 2.5 渲染图入口

```cpp
class RenderGraphBase : ObjectBase, PassPool, ResourcePool, ResultPool, DeviceObjectBase {
    void SetCanvasSize(extent);   // 改变会触发 kCanvasResized
    virtual void PreExecute() const {}  // 每帧执行前钩子(更新外部资源/映射数据)
    void CmdExecute(command_buffer);    // 编译 + 执行
};
```

## 3. 执行器(executor/default/)

执行器把声明式渲染图**编译**为可执行结构,分 7 个阶段,每个阶段是一个独立结构体,事件驱动增量重编译:

```
Collection → Dependency → Metadata → Schedule
                                     → VkAllocation → VkCommand
                                                    → VkDescriptor
```

### 3.1 Collection — 收集

把渲染图中的所有对象(Pass/Resource/Input)按 `GlobalKey` 收集成快照,供后续阶段查询。`ClearInfo` 重置每个对象的执行器缓存。

### 3.2 Dependency — 依赖分析(图构建)

这是框架最核心的算法阶段:

1. **遍历输出别名建图**:从 result 出发递归 `traverse_output_alias → traverse_pass`,对每个 Pass 的每个 Input:
   - 若 input 引用另一个 Pass 的 output(OutputAlias),则 `m_pass_graph` 加边 `src_pass → dst_pass`;
   - 若引用原始资源(RawAlias),则 `m_resource_graph` 加资源顶点,若资源是 Combined,则对每个子别名递归加边。
   - **环检测**:若遍历中遇到 `p_resource` 为空(说明源 Pass 还在栈上),抛出 `PassNotDAG`。
2. **加 WAR 边**:对每个 Pass,收集其读/写同一资源的边;若存在"先读后写"则加读→写的边;并把原写边标记为 `kIndirectWAW`(间接 WAW,供调度阶段判断可否合并)。
3. **拓扑排序**:Kahn 算法,分配 `topo_id`;非 DAG 抛错。
4. **资源树解析**:资源间(Combined 的父子)构成森林,标记 `root_id`,每个子资源归到根资源。
5. **关系闭包**:计算 Pass×Pass、Pass×RootResource、RootResource×RootResource 的**传递闭包关系**(bitset 矩阵),供调度阶段 O(1) 判断"谁在谁之前"。
6. **加 image-read 边**:同图多个读(如第一个读为 InputAttachment、第二个读为 Sampler)可能破坏合并,额外加边约束。

> 注释要点:`Relation` 用 bitset 行存储,`All(row)` 做按位与判断"对所有元素成立",把 O(n²) 的朴素判断降到 O(n/64) 位运算。

### 3.3 Metadata — 元数据推导

- **资源分类**:外部资源 / 内部资源 / 内部根资源;
- **外部资源信息**:从 myvk::ImageView/Buffer 反推 size/format/usage;
- **尺寸与对齐计算**:对 Combined 资源递归合并子尺寸(buffer 按字节偏移拼接,image 按 array layer 拼接),`base_layer` 逐层累计;
- **创建 usage 汇总**:遍历所有 Pass 的输入,按 Usage 的 `resource_creation_usages` 把位或进根资源的创建 usage;
- **RenderArea 推导**:GraphicsPass 若未显式设 RenderArea,则取所有附件尺寸的最大值。

### 3.4 Schedule — 调度(子通道合并 + 屏障)

**Pass 合并成 RenderPass 子通道**是提升性能的关键:

1. `merge_passes`:计算每个 Pass 的 `merge_size`——
   - 仅当相邻两个 Pass 都是 Graphics 且 RenderArea 相等才可能合并;
   - 遍历依赖边,取约束的最小值:若边的两端访问"可合并"(同为附件且访问同一资源),允许跨越边合并;image-read 边若读布局相同也可合并;否则必须在边处断开;
   - "Regularize"把 merge_size 归一化(只能 +1 增长);
2. `make_pass_groups`:按 merge_size 分组,组内 Pass 依次成为子通道(subpass 0,1,2…);
3. `make_barriers`:对每个资源,分析其访问序列(读、写、读写):
   - 写→写之间插 `kWRWBarrier`(WAW);
   - 读/写→后续写插读写屏障;
   - 屏障记录 src/dst stage + access(从 Usage 查表),按资源类型分别生成 image/buffer barrier 模板;
4. `finalize_last_inputs`:把"最后一个访问"的输入状态(如 loadOp 未使用时的布局)固定下来;
5. `make_output_barriers`:为 result 输出(如 swapchain 的 PRESENT_SRC)追加屏障;
6. `check_ext_read_only`:校验外部资源是否被意外写。

屏障被记录在 `PriorBarrier`(每个 PassCmd 执行前)与 `PostBarrier`(整图结束后)中。

### 3.5 VkAllocation — 内存分配

- 为每个**根内部资源**调用 myvk 的 `Buffer::Create` / `Image::Create` 分配设备内存;
- ManagedBuffer 若 `SetMapped(true)` 则分配主机可见内存并记录映射指针;
- 子资源(Combined 成员)共享根分配,通过 `GetVkImageView` / `GetBufferView` 暴露 offset/layer 切片视图。

### 3.6 VkDescriptor — 描述符生成

- 为每个 Pass(有描述符输入者)生成 `VkDescriptorSetLayout`(按 binding + Usage 查表得描述符类型);
- 生成并更新 `VkDescriptorSet`:每次执行前调用 `VkUpdateExternal` 把外部资源的 ImageView/Buffer 写进描述符(见 VkRunner::Run);
- `UpdatePipeline` 时保证 layout 与 set 一致。

### 3.7 VkCommand — 命令序列生成

把 schedule 结果落成可执行命令:

- **RenderPass 组装**(`Builder::pop_pass`):对每个 PassGroup,
  - 收集附件(颜色/深度/输入附件)、子通道描述、子通道依赖;
  - 生成 `myvk::RenderPass`(含 loadOp/storeOp、布局转换、依赖);
  - 生成 `myvk::Framebuffer`(ImagelessFramebuffer,见 04 文档);
- **管线创建**:`CreatePipeline` 惰性调用 Pass 的 `CreatePipeline()` 并缓存;GraphicsPass 还会把 subpass 序号传入管线构造;
- 生成 `PassCmd{ prior_barriers, myvk_render_pass, myvk_framebuffer, subpasses, attachments, has_clear_values }` 序列。

### 3.8 VkRunner — 执行

```cpp
Run(command_buffer, args):
  update_ext_cache(args)                  // 检测外部资源是否换绑
  vk_descriptor.VkUpdateExternal(...)     // 更新外部资源描述符
  for pass_cmd in GetPassCommands():
      cmd_pipeline_barriers(prior_barriers)   // 执行前屏障
      if 是 RenderPass:
          vkCmdBeginRenderPass(attachment 列表 + clear values)
          执行子通道 0;vkCmdNextSubpass 依次执行其余子通道
          vkCmdEndRenderPass
      else:
          run_pass(该 Pass)               // 创建管线 + 调 CmdExecute
  cmd_pipeline_barriers(GetPostBarriers()) // 图结束屏障
```

其中 `run_pass` 为每个 Pass 先 `VkCommand::CreatePipeline(p_pass)`(惰性创建)再执行用户 `CmdExecute`。用户代码只写"绑定管线/描述符/push constant/分发",**屏障与附件切换完全由框架负责**。

## 4. 框架 API 速查(应用视角)

| 方法 | 作用 |
| --- | --- |
| `CreateResource<ManagedImage>({key}, format)` | 建内部图像 |
| `CreateResource<ManagedBuffer>({key})` / `({key}, size)` | 建内部缓冲,可 `SetSizeFunc` 按 canvas 变尺寸、`SetMapped(true)` 映射 |
| `CreateResource<InputImage>({key}, view)` | 引用外部图像 |
| `CreateResource<InputBuffer>({key}, buffer)` | 引用外部缓冲 |
| `CreateResource<AccelerationStructure>({key}, as)` | 引用加速结构(缓冲形式) |
| `CreateResource<SwapchainImage>({key}, frame_manager)` | 引用交换链图像 |
| `CreatePass<T>({key}, args...)` | 创建 Pass |
| `GetPass<T>({key})` | 取回 Pass |
| `res->Alias()` | 得到可传给 Pass 的只读引用 |
| `MakeImageOutput({key})` / `MakeBufferOutput({key})` | 把某输入声明为"输出"供下游引用 |
| `AddResult({key}, image)` | 声明最终输出(result) |
| `PreExecute()` | 每帧钩子:更新外部资源、重置计数等 |

## 5. 设计评价

**优点**:
- 增量编译,运行时开销低(编译阶段缓存在 `m_p_executor_info` 中,仅在相关事件发生时重建);
- 一个 `Usage` 枚举驱动全部下游决策,一致性高、扩展容易(加一个新 usage 只需改表);
- 子通道自动合并 + 屏障自动生成,把 Vulkan 同步的正确性风险集中到框架一处;
- Combined 资源别名机制省显存(临时图像共享)。

**代价/注意点**:
- 事件系统是"全量重编译"式的:任何 Pass 变化都会级联重编整个依赖链(源码中 `exe_compile_flags` 的传递闭包逻辑);
- 结构体内存布局需 CPU/GLSL 手工对齐(如 `NRCEvalRecord`、`Material`、`Transform`);
- 框架强依赖 C++20 特性(concept、span、折叠表达式),编译要求较高。
